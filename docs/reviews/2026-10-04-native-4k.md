Date: 2026-10-04. Scope: personal `gancoe/SmartTubeIOS` fork, `native-tvos` branch.

## Diagnosis and evidence

The user reports that known 4K videos offer only 1080p. The existing VisionOS HLS policy deliberately filters to H.264 and a maximum height of 1080. Measured source and test evidence: `HLSPlaybackPolicy.swift`, `VisionOSPlaybackTests`, and the failing pre-change policy run in `tmp/native-4k-policy-red.log`.

The alternative that YouTube supplied no accessible 4K stream is ruled out for the sampled video `CyEoXiiZZgc`. An anonymous watch-session seed followed by the VisionOS player request returned a VP9 profile 0 HLS variant at 3840 by 2160. The master, 4K playlist and bounded 1024-byte media sample each returned HTTP 200. The probe did not save signed URLs or session tokens. Measured artifact: `tmp/native-4k-live-probe-CyEoXiiZZgc.json`, UTC `2026-10-04T03:51:55.130365+00:00`. This proves availability for that request, not sustained playback or universal stream availability.

The sampled master has H.264 through 1080p and VP9 through 2160p. The player metadata also advertises AV1, but the master does not supply an AV1 HLS variant. YouTube's VP9 metadata uses `codecs="vp9"`, whereas the HLS master uses the profile-specific `vp09.00.50.08` token.

Decoder support on the user's physical Apple TV remains UNVERIFIED. `devicectl` listed simulated devices, not a verified hardware identity. The sideloading service did not return a populated product type or OS version. The new in-app Device, Decoder hardware and VP9 opt-in rows provide the direct check needed.

## Native decoder experiment

Apple's installed SDK declares [VTRegisterSupplementalVideoDecoderIfAvailable](https://developer.apple.com/documentation/videotoolbox/vtregistersupplementalvideodecoderifavailable(_:)) on tvOS 26.2 and later. This API opts into an available supplemental decoder. [WebKit's VP9 utilities](https://github.com/WebKit/WebKit/blob/main/Source/WebCore/platform/graphics/cocoa/VP9UtilitiesCocoa.mm) register VP9 and query hardware support. This is evidence for trying the public API, not proof that our AVPlayer HLS route can decode VP9.

The patch requests that registration once, under an OS availability guard, records the hardware query before and after registration, and attempts the native 4K HLS route only when the user explicitly selects 2160p, registration was requested, the post-request VP9 hardware query returns true, and the route has not been rejected for this view-model session. Auto and other quality preferences retain the existing H.264 path.

[Apple's HLS authoring specification](https://developer.apple.com/documentation/http-live-streaming/hls-authoring-specification-for-apple-devices/) section 1.1 lists H.264, HEVC, Dolby Vision and AV1, excluding VP9. This is stronger evidence that hardware decoder registration alone does not establish native HLS compatibility. The patch is an opt-in diagnostic experiment, not a supported VP9 HLS claim. Measured primary-source read: `tmp/apple-hls-authoring.md:88`.

The native manifest permits H.264 and VP9 profile 0 up to 2160p. AV1 and VP9 profile 2 remain excluded. The same filter is used for initial playback and quality changes. Quality choices must have a height present in the filtered master; bare VP9 metadata can describe those choices without opening its WebM DASH URL. Filtered variant caches are separate for native 4K and H.264 fallback. The existing quality preference is preserved. To enter the experiment, choose Settings > Default Quality > 2160p before opening the video. Auto does not opt into it. If the hardware gate fails, even the 2160p preference uses the capped H.264 fallback.

`VisionOSNativeStreamSource` fetches the player response once and falls back with that response if the initial native HLS attempt fails. A ready item is not evidence of successful decoding throughout the video. A persistent failure observer handles late native VP9 failures, including media-services resets. It preserves the pending/current position, rejects further native VP9 attempts for the view-model session, releases the failed item or rebuilds the reset player, and retries through the existing fallback chain. Rapid-stall escalation also rejects VP9 and preserves position. Initial failures remain with the source fallback. Loading another video, stopping or suspending cancels the recovery task. Physical failure recovery, seeking, sustained playback and remote behaviour remain device checks.

## What other projects do

- [MuTube](https://github.com/Exaphis/mutube/blob/main/README.md) patches a decrypted YouTube TV app and injects TizenTube functionality for ad removal and SponsorBlock. It inherits the existing TV interface. Its [patcher](https://github.com/Exaphis/mutube/blob/main/patcher.py) uses binary offsets and codec-support patches, so maintenance is tied to the target app build. Its issue tracker contains [1080p limits](https://github.com/Exaphis/mutube/issues/1) and [HDR playback problems](https://github.com/Exaphis/mutube/issues/2). Those reports do not establish this native HLS route's behaviour.
- [Yattee](https://github.com/yattee/yattee/blob/main/README.md) builds an independent SwiftUI interface. Its [published app manifest](https://github.com/yattee/yattee/blob/main/altstore-source.json) describes MPV playback of H.264, HEVC, VP9 and AV1, with YouTube streams supplied by Invidious, Piped or a self-hosted server. This separates stream extraction from playback and is a relevant alternative if the public native decoder experiment fails.
- [AetherEngine](https://github.com/superuser404notfound/AetherEngine) separates FFmpeg demuxing and decoding from the UI, using an AVPlayer route for supported codecs and a sample-buffer display route for software codecs. Its current README places VP9 on the software route. This further supports investigating a separate player route rather than equating VideoToolbox capability with HLS support.
- [KSPlayer](https://github.com/kingslay/KSPlayer) offers Apple-platform AVPlayer and FFmpeg playback components. It is a possible player implementation reference, not a solution to YouTube authentication or stream availability by itself.

Recommendation: keep the native app and use MuTube as a fallback and interaction benchmark. Validate the smallest native decoder experiment first. If the physical TV cannot use it, consider a separately scoped MPV/FFmpeg player plus a controlled stream backend. Do not advertise 4K or HDR as fixed based on manifest access, a capability query or simulator tests.
